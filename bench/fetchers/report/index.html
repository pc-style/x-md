Notes

  • Verdict: the self-hosted fxtwitter fork (PR #98) is the only prototype that matches production's data (100% of post checks, 95% of profile checks), is about 6× faster than production on profiles, and absorbed the burst without a single error. Syndication (PR #102) is the fastest for posts (~5× faster than production) but loses author profile data on posts, its /user serves old popular posts instead of recent ones, and it 503s under load. Operator-session GraphQL (PR #99) is fast and reliable per request but drops author counts, one quote and a join date, and its 30-per-15-minute per-IP budget is the binding limit.
  • Production itself was flaky: 5 of 8 public profiles answered 503 upstream_unavailable on the first pass and needed a retry for a baseline; the deleted and never-existing posts return 502 firecrawl_error instead of 404; @emma (protected) and the missing handle return 503.
  • Protected posts: no public route exposes a protected post's id, so protected is covered at profile level (@emma). Only the GraphQL prototype returned @emma's header with protected: true (after the window reset); every other target, production included, answered 503.
  • GraphQL budget: the main run hit the prototype's own per-IP limit after 27 uncached requests (one 503 retry counted), so @vercel, @emma and the missing handle were retried 16 minutes later; those cells say so. In the burst it 429'd from request 27 with Retry-After: 867. Its 60 s cache answers repeats in ~20 ms.
  • Syndication specifics: GIFs arrive under media.animated (counted as video here); thread walk stops at parents, so a post's later self-replies are missing (2 fixtures); posts carry no author follower counts.
  • fx self-host specifics: its /user/jack returned only 3 posts in the main run (a short timeline page), the one profile miss. Its "repeat" is not cached (~0.9 s).
  • Single region (EU VM), one sample per item per pass; p95 over ~18 posts / ~8 profiles is indicative, not tight.
